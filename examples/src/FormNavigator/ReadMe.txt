============================================================
FormNavigator — Серия проектов с пошаговой эволюцией MVP
Borland C++ Builder 6.0 / C++98
============================================================

Архив содержит 4 проекта, каждый следующий добавляет
архитектурное улучшение к предыдущему. Все проекты решают
одну задачу: навигация между тремя VCL-формами (Home, Data,
Result) с передачей общих данных (SharedData) по паттерну MVP.


01 — Flat-MVP
-------------
Один проект (.bpr), единый Presenter, отдельная Model.

  • Один Presenter знает все три вида (IHomeView, IDataView,
    IResultView) и управляет навигацией через switchTo().
  • Отдельная модель (AppModel) с сигналом onDataChanged.
  • Формы создаются заранее и живут вечно (show/hide).
  • signal_impl: .h + .cpp.
  • SharedData (NavigatorTypes): .h + .cpp.

Главная идея: базовый MVP «в лоб» — один презентер на всё
приложение, прямая связь Presenter <-> Model.


02 — MVP-Navigator
------------------
Один проект (.bpr), отдельные Presenter'ы + Навигатор.

  • Каждый экран получает свой Presenter (HomePresenter,
    DataPresenter, ResultPresenter).
  • Навигатор (AppNavigator) создаёт MVP-триады и управляет
    жизненным циклом (initialize/destroy).
  • Модель (AppModel) убрана — данные передаются через
    параметры навигации (SharedData).
  • IPresenter: initialize() + destroy() для подписки/отписки.
  • Добавлен сигнал viewClosed (кнопка X на форме).
  • Формы по-прежнему живут вечно.

Главная идея: разделение ответственности — каждый презентер
знает только свой вид и навигатор. Паттерн «Навигатор».


03 — MVP-Navigator-Modular
--------------------------
Группа проектов (.bpg): Shared + Business.lib + Forms.lib + App.exe.

  • Модульная сборка: Shared (header-only), Business.lib
    (презентеры), Forms.lib (VCL-формы), App.exe (навигатор).
  • Create-on-demand: формы создаются при навигации,
    а не заранее. DataForm и ResultForm — через new,
    освобождаются через releaseView (TForm::Release).
  • HomeForm создаётся через Application->CreateForm()
    и назначается MainForm — живёт вечно.
  • signal_impl — header-only (было .h + .cpp).
  • SharedData — header-only (было .h + .cpp).
  • Таблица форм (s_formTable) устраняет switch-case.
  • Тот же Application->Run() для цикла сообщений.

Главная идея: модульность + create-on-demand. Формы не
существуют, пока не понадобятся. Корректное освобождение
ресурсов через TForm::Release.


04 — MVP-Navigator-History
--------------------------
Та же модулярная структура + стек навигации (Back Stack).

  • Стек навигации: при движении «вперёд» текущая форма
    помещается в стек как точка возврата; при закрытии
    (кнопка X) — возврат на предыдущую форму из стека.
  • Иерархическая навигация: если целевая форма уже есть
    в стеке — стек обрезается до неё (движение «вверх»).
  • closeCurrentView: при пустом стеке — завершение
    приложения, иначе — навигация «назад».
  • Все формы создаются через new (включая HomeForm).
    Главная форма определяется первой навигацией,
    а не Application->CreateForm().
  • Собственный цикл сообщений (navigator.Run()) вместо
    Application->Run() — для контроля завершения.
  • INavigator перенесён из Shared/ в Business/
    (презентеры — основные потребители).
  • Параметры навигации: const void* вместо const SharedData&
    (навигатор не знает конкретный тип данных).
  • Защита от перехода на самого себя (m_currentType check).

Главная идея: навигация с историей — кнопка X возвращает
на предыдущий экран, а не всегда на HomeForm.
